Background

Motivation & Inspiration

The "Why"
📖 The Pedagogical Problem

In academic courses, graph algorithms are often presented through static textbook node-edge diagrams or chalkboard step-throughs. Students struggle to develop an intuitive mental model for concepts like search-frontier expansion, heuristic bias, and edge relaxation under real spatial constraints.

🏙️ The Real-World Inspiration

Real navigation systems (Google Maps, autonomous vehicles, game engine NavMeshes) route through complex physical terrain with skyscrapers, traffic penalties, and dynamic barriers. Most existing educational visualizers are flat 2D grids of colored squares. We were inspired to build a GPU-accelerated 3D miniature city that makes algorithms tangible.

🎯 Core Philosophy: Theory Meets Real Engineering

Provide an uncompromised full-stack application that simultaneously serves as an interactive pedagogical tool, a high-performance graphics showcase (60 FPS), and an empirical benchmark suite.

Project Objectives

Aims & Goals
1. Algorithm Diversity

Implement and visualize 6 foundational graph algorithms: BFS, DFS, Dijkstra, A*, Greedy Best-First, and Bidirectional BFS with strict adherence to data structure specifications.

2. Procedural Mazes

Implement 5 distinct maze generation strategies (Recursive Division, DFS Backtracker, Prim's, Kruskal's, Random) with an automated guaranteed solvability validator.

3. 3D Spatial Rendering

Render a 25×50 grid (1,250 nodes) with InstancedMeshes and spring physics in WebGL/Three.js, modeling walls as buildings and weights as parks.

4. Empirical Analytics

Track live performance metrics including Nodes Visited, Path Length, Traversal Cost, and Execution Time (ms) with comparative charting.

5. Persistence & Sharing

Build a RESTful API backed by Neon serverless PostgreSQL allowing users to save and share custom grid layouts via unique UUID links.

6. Production Standards

Enforce strict TypeScript types, zero-allocation render loops, defensive input validation, responsive controls, and high-contrast dark aesthetic.

System Design

Architecture & Execution Pipeline

Separation of Concerns
1

User Interaction & Zustand Store

User selects algorithm, places obstacles, or loads a maze. State is centrally dispatched.

2

Pure Synchronous Algorithm Run (~2ms)

Pure mathematical execution in memory. Zero setTimeout or UI interference. Produces AlgorithmResult.

3

AnimationEngine (GSAP Timeline)

Builds a staggered timeline writing values into flat, shared Float32Array memory buffers.

4

Three.js Render Loop (60 FPS)

useFrame() reads buffers directly. Updates InstancedMesh matrices using spring physics.

💡 Why This Pipeline Wins
  • Zero GC Stutter: No React state updates during the 1,250-node traversal loop.
  • Dynamic Speed Scrubbing: timeline.timeScale() changes speed instantly without restarting.
  • Race Condition Immunity: Monotonic runId invalidates previous runs if user clicks "Run" repeatedly.
  • Deterministic Benchmarking: Execution time measured via performance.now() before rendering begins.

Algorithm Analysis

Pathfinding Algorithms Overview

Theoretical Matrix
Algorithm Data Structure Supports Weights? Optimal Shortest Path? Time Complexity Space Complexity
Breadth-First Search (BFS) Queue (FIFO) No Yes (Unweighted) O(V + E) O(V)
Depth-First Search (DFS) Stack (LIFO) No No O(V + E) O(V)
Dijkstra's Algorithm Min-Heap (Priority Queue) Yes Yes O((V + E) log V) O(V)
A* Search Min-Heap (f = g + h) Yes Yes (Admissible) O((V + E) log V) O(V)
Greedy Best-First Search Min-Heap (f = h) No No O((V + E) log V) O(V)
Bidirectional BFS 2 × Queues + 2 × Sets No Yes (Unweighted) O(V + E) O(V)
* Note: On our 25×50 grid, \(V = 1,250\) vertices and \(E \le 4V = 5,000\) edges due to 4-cardinal orthogonal adjacency.

Core DSA Deep Dive

Dijkstra vs. A* Search: Heuristic Power

Evaluation Functions
Dijkstra's Algorithm
Priority = g(n)
// Uninformed blind search
Expands in concentric radial circles.
Has zero knowledge of target location.

Guarantees shortest path on non-negative weighted graphs, but wastes computation exploring nodes that lead away from the destination.

A* Search
Priority = f(n) = g(n) + h(n)
// Informed heuristic search
g(n) = Exact cost from Start to n
h(n) = Estimated cost from n to Target

Biases the search beam directly toward the goal. Explores up to 70% fewer nodes while yielding the exact same optimal cost.

📐 Manhattan Distance Heuristic & Admissibility Guard

Because our grid only permits 4 cardinal moves (no diagonals), the Manhattan distance \(h(n) = |\Delta \text{row}| + |\Delta \text{col}|\) is strictly admissible (\(h(n) \le h^*(n)\)) and consistent (monotonic). In our implementation, we multiply by the grid's minimum cell weight to guarantee that \(h(n)\) never overestimates in weighted scenarios.

Procedural Generation

Maze Generation & Solvability Guarantee

Spanning Trees
Recursive Division

Chamber subdivision. Starts with borders; draws horizontal/vertical dividing walls with random passage gaps. Creates distinct rooms and corridors.

DFS Backtracker

Randomized depth-first carving moving 2 cells at a time. Backtracks via stack on dead ends. Produces deep, winding corridors with high bottlenecking.

Randomized Kruskal's

Treats cells as disjoint sets. Shuffles wall edges using Fisher-Yates. Uses Union-Find (DSU) with Path Compression & Rank to unite sets without cycles.

🛡️ The Solvability Guard: 0-1 Dijkstra Post-Processor

Random generators can inadvertently isolate the target. Our custom ensureReachableMaze algorithm runs a BFS reachability test. If disconnected, it executes a 0-1 Dijkstra search (moving on open passages costs 0, tunneling through walls costs 1) to identify the absolute minimum sequence of blocking walls and converts them into passages.

Engineering Challenges

Difficulties Faced & How We Solved Them

Key Viva Question
1. WebGL 60 FPS Bottleneck

Problem: Rendering 1,250 individual 3D meshes caused 1,250 draw calls per frame, tanking the browser to 15 FPS.
Solution: Converted to THREE.InstancedMesh for roads, buildings, and trees. Collapsed 1,250 draw calls into just 3 draw calls.

2. React State Thrashing

Problem: Triggering React component re-renders for every visited node froze the main thread.
Solution: Decoupled execution. GSAP timeline writes to flat Float32Array buffers that Three.js reads directly in useFrame() without React re-renders.

3. MinHeap Priority Invalidation

Problem: Mutating node distances in-place corrupted the heap order without an expensive \(O(N)\) rebuild.
Solution: Stored immutable snapshot objects { node, distance } and added a stale-entry check on pop: if (entry.distance !== node.distance) continue;.

4. Asynchronous Race Conditions

Problem: Users spamming "Run" or "Reset" during animation left orphaned timer callbacks corrupting the board.
Solution: Implemented a monotonic runId check on all async steps, instantly dropping stale executions.

Critical Evaluation

Limitations & Future Roadmap

Project Evolution
Current Limitations
  • Topology: Uniform 2D grid only (no arbitrary DAGs or non-grid graphs).
  • Movement: 4 cardinal directions only; no diagonal traversal.
  • Negative Weights: Cannot handle negative edge weights (requires Bellman-Ford).
  • Fixed Grid: 25×50 dimensions are fixed in the current UI.
Future Roadmap
  • 8-Directional & Continuous: Add diagonal moves with Octile distance heuristics and Theta* smoothing.
  • Dynamic Environments (D* Lite): Real-time obstacle replanning while agents are in transit.
  • Real GIS Road Import: Import actual road networks from OpenStreetMap API.
  • Replay Scrubbing: Step forward and backward through the priority queue state node-by-node.
